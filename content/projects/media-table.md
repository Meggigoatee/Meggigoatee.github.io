## 프로젝트 핵심 스택

미디어테이블은 카메라 영상에서 테이블 위의 컵을 감지하고, 컵의 위치와 색상에 맞춘 애니메이션을 화면에 합성하는 전시용 데스크탑 애플리케이션입니다. 카메라 수신부터 객체 감지, 추적, 화면 좌표 보정, PixiJS 효과 재생까지 하나의 실시간 파이프라인으로 구성되어 있습니다.

- 카메라 영상 수신: WebRTC/WHEP와 `VideoFrame`
- 객체 감지: Web Worker 안의 ONNX Runtime Web 추론
- GPU 처리: WebGPU 전처리와 추론, WASM 대체 경로
- 상호작용 상태: 컵 위치 추적과 생성·유지·제거 이벤트
- 좌표 캘리브레이션: OpenCV.js ChArUco 보드 측정과 TPS·호모그래피 변환
- 화면 출력: PixiJS 아틀라스 애니메이션과 테이블 배경 영상
- 실행 형태: Electron 기반 Windows 애플리케이션

## 배경과 해결하려던 문제

이 프로젝트가 다루는 핵심 과제는 카메라에서 관찰한 물리 객체와 대형 화면의 그래픽 반응을 지연 없이 연결하는 것입니다. 단일 프레임의 감지 결과를 바로 사용하는 것만으로는 흔들림이나 일시적인 누락이 시각 효과의 깜빡임으로 이어질 수 있고, 카메라 좌표와 실제 출력 화면 좌표도 그대로 일치하지 않습니다.

따라서 영상 입력, 추론, 추적, 좌표 변환과 효과 재생을 분리하면서도 다음 단계가 하나의 연속된 경험으로 동작하도록 구성했습니다.

- 렌더링 흐름을 막지 않고 카메라 프레임을 처리할 것
- 밀린 프레임보다 최신 프레임을 우선해 체감 지연을 제어할 것
- 여러 프레임의 결과를 안정화해 효과의 생성과 제거 시점을 결정할 것
- 카메라에서 얻은 좌표를 실제 출력 화면에 맞게 보정할 것
- 큰 애니메이션 에셋을 재생 중 끊김 없이 공급할 것

## 담당 범위

사내 프로젝트의 전체 개발을 담당했습니다. Electron 애플리케이션 수명 주기와 로컬 카메라 프록시 실행, Vue 기반 운영 화면, Worker 객체 감지 파이프라인, 추적과 ChArUco 좌표 캘리브레이션, PixiJS 효과 재생, 에셋 패킹과 Windows 패키징을 구현했습니다. 기획과 디자인에는 참여하지 않았습니다.

## 시스템 흐름

카메라 프레임이 메인 렌더링 흐름과 분리된 Worker에서 분석되고, 안정화된 감지 위치는 ChArUco 보정 데이터와 TPS 변환을 거쳐 PixiJS 장면의 화면 좌표로 전달됩니다.
상단 다이어그램은 Camera Input부터 Display Output까지 각 단계의 처리 책임과 다음 단계로 전달되는 결과를 순서대로 보여줍니다.

## 핵심 구현

### 1. 최신 프레임을 우선하는 Worker 파이프라인

카메라 스트림은 `MediaStreamTrackProcessor`를 통해 `VideoFrame` 단위로 읽습니다. 메인 스레드의 감지 서비스는 카메라별 목표 FPS를 적용하고, 처리 가능한 프레임만 Worker로 전송합니다.

Worker가 바쁜 동안 같은 카메라의 새 프레임이 도착하면 이전 대기 프레임을 닫고 최신 프레임으로 교체합니다. 처리량보다 입력이 빨라졌을 때 오래된 프레임이 쌓여 상호작용이 뒤늦게 반응하는 상황을 피하기 위한 지연 우선 구조입니다. 처리하거나 버린 `VideoFrame`을 명시적으로 닫아 디코더 자원이 계속 점유되지 않도록 했습니다.

### 2. WebGPU 전처리와 ONNX 추론

추론 엔진은 프레임을 모델 입력 크기에 맞게 letterbox 처리하고 RGB 정규화와 NCHW 변환을 수행합니다. WebGPU 경로에서는 이 과정을 GPU 버퍼에서 처리한 뒤 `ort.Tensor.fromGpuBuffer()`로 ONNX Runtime Web 입력에 연결합니다. WebGPU 전처리를 초기화할 수 없는 환경에는 CPU 전처리 경로를 남겼고, 추론 실행 공급자도 WebGPU 다음에 WASM을 사용하도록 구성했습니다.

모델 출력은 신뢰도 필터링과 NMS를 거쳐 원본 프레임 좌표로 복원됩니다. 감지된 컵 영역의 대표 색상을 CIE Lab 공간에서 비교해 효과 라벨을 선택하는 별도 분류 단계도 포함됩니다.

### 3. 감지 결과를 안정적인 상호작용 상태로 변환

카메라별 추적기는 가까운 위치의 감지를 기존 객체와 연결하고, 연속 감지 횟수와 색상 투표 조건을 만족한 객체에만 활성 ID를 부여합니다. 활성화된 객체는 생성·유지·제거 이벤트로 변환되어 화면 상태 저장소에 반영됩니다. 이 과정은 일시적인 감지 누락과 색상 변화가 곧바로 효과 깜빡임이나 라벨 변경으로 이어지는 것을 줄이는 역할을 합니다.

### 4. ChArUco 보드로 맞춘 현실 평면과 화면 좌표

카메라가 보는 테이블 평면과 프로그램의 출력 좌표는 원근, 설치 각도와 렌즈 특성 때문에 그대로 일치하지 않습니다. 캘리브레이션 모드에서는 일반 감지를 잠시 멈추고 카메라별 보정 프레임을 캡처합니다. OpenCV.js의 ChArUco detector가 보드의 코너와 ID를 검출하고, 카메라 픽셀 좌표 `pts_cam`과 보드 기준 화면 좌표 `pts_screen`의 대응점을 구성합니다.

각 카메라에서 가장 많은 유효 코너가 잡힌 측정값을 선택하고, 모든 카메라의 측정이 성공했을 때 대응점과 RANSAC 호모그래피를 저장합니다. 런타임 좌표 변환은 대응점이 3개 이상이면 TPS를 우선 사용해 국소 왜곡까지 흡수하고, 불가능하면 3×3 호모그래피, 마지막에는 원본 좌표를 사용합니다. 새 보정값을 적용할 때 진행 중인 프레임과 추적 상태를 초기화해 서로 다른 좌표계의 결과가 섞이지 않게 했습니다.

### 5. PixiJS 효과와 아틀라스 자산 파이프라인

각 효과는 `created`, `updated`, `deleted` 세 단계의 애니메이션으로 구성됩니다. 원본 PNG 프레임은 별도 패커가 고정 크기의 그리드 시트와 manifest로 변환하며, 런타임은 manifest의 FPS, 반복 여부와 프레임 수를 기준으로 재생합니다.

설정된 효과 아틀라스는 감지 시작 전에 순차적으로 로드하고 GPU에 업로드합니다. 실행 중 페이지 로드로 인한 끊김을 피하는 대신 시작 시간과 메모리를 사용하는 선택입니다. PixiJS 효과는 추적된 중심 좌표를 따라가며, 컵 중심에는 마스크와 커버 레이어를 적용해 그래픽이 물리 컵 영역을 침범하지 않도록 구성했습니다. 컵이 새로 놓이면 좌우 테이블 영역에 대응하는 배경 영상도 별도로 한 번 재생할 수 있습니다.

## 기술 선택과 트레이드오프

- **Electron과 브라우저 GPU 스택:** Vue 운영 UI, WebRTC, Web Worker, WebGPU와 PixiJS를 한 애플리케이션에서 연결할 수 있습니다. 반면 GPU 자원과 프레임 수명 주기를 애플리케이션에서 세심하게 관리해야 합니다.
- **최신 프레임 우선 큐:** 모든 입력 프레임의 처리를 보장하지 않는 대신, 오래된 결과가 늦게 표시되는 것을 피하고 실시간 반응성을 우선합니다.
- **WebGPU 우선, CPU·WASM 대체 경로:** 지원 환경에서는 GPU 경로를 사용하면서도 초기화 실패에 대비할 수 있습니다. 대체 경로별 성능 차이는 배포 장비에서 별도로 검증해야 합니다.
- **ChArUco 대응점과 TPS:** 화면 전체의 국소 왜곡을 보정할 수 있지만, 보정 중에는 일반 감지를 잠시 중단하고 각 카메라에서 보드의 유효 코너를 충분히 확보해야 합니다. 측정 실패에 대비해 호모그래피와 원본 좌표 대체 경로를 유지했습니다.
- **공유 Worker와 카메라별 Worker:** 하나의 추론 세션을 공유해 자원을 줄이는 구성과 카메라별 실행을 분리하는 구성을 설정으로 선택할 수 있습니다.
- **아틀라스 전체 사전 로드:** 전시 중 로딩 변수를 줄이는 대신 초기 로드 시간과 GPU 메모리를 사용합니다. 현재 구현은 실행 중 안정성을 우선해 사전 로드 방식을 택했습니다.

## 테스트·배포·운영 안정성

Vitest는 Electron main, preload와 Vue renderer 환경을 나눈 프로젝트 설정을 사용합니다. 저장소에는 설정 검증, 감지 서비스, 객체 추적, 전처리, YOLO 디코드, 색상 분류, TPS·호모그래피 좌표 변환, WebGPU 프로파일링, 아틀라스 로딩, 효과 재생과 상태 저장소를 대상으로 한 테스트가 있습니다. 현재 초안 작성 과정에서는 전체 테스트 통과 여부를 새로 검증하지 않았습니다.

Windows 배포는 Electron Builder의 NSIS 설치형과 portable 빌드 스크립트로 구성되어 있으며, 모델·런타임·아틀라스 같은 실행 자원을 애플리케이션과 함께 배치합니다. 현재 오픈 전 전시 환경에 시범 설치해 운영하고 있습니다.

운영 안정성을 위해 코드에서 확인되는 장치는 다음과 같습니다.

- 카메라 연결 재시도와 로컬 프록시 프로세스의 시작·종료 관리
- 목표 FPS 초과 또는 처리 불가능한 프레임의 즉시 해제
- 효과 자산 준비 이후 감지 파이프라인을 시작하는 부팅 순서
- 설정 저장 전 타입, 범위와 중복 값을 검사하는 검증 계층
- 디스플레이 절전과 백그라운드 렌더링 제한을 방지하는 Electron 실행 설정

## 의사결정과 결과

### 문제

카메라 스트림 지연과 객체 추론 지연이 누적되어, 사용자가 테이블에 물체를 배치한 뒤 투사 효과가 나타날 때까지 3초 이상 걸렸습니다. 물리적인 행동과 화면 반응이 분리되어 보일 만큼 긴 지연이었습니다.

### 대안 소개

- 더 높은 성능의 카메라와 PC로 하드웨어를 교체하는 방식
- 카메라 스트림 프로토콜을 변경하고 데이터 전달과 추론 파이프라인을 최적화하는 방식

### 결정 이유

하드웨어 교체보다 프로토콜과 처리 구조 개선을 선택했습니다. Python 기반 OpenCV·FFmpeg 스트림을 MediaMTX의 WebRTC 입력으로 바꿔 영상 전송 지연을 줄였습니다. 또한 별도 프로세스의 표준 출력과 IPC에 의존하던 감지 데이터 전달을 없애고, ONNX Runtime Web을 도입해 추론과 후속 처리를 Electron 렌더러 계층에서 수행하도록 통합했습니다. 장비를 교체하지 않고도 병목을 직접 줄일 수 있고, 프로세스 사이의 데이터 이동도 단순화할 수 있었기 때문입니다.

### 결과

카메라 스트림 지연은 약 1.2초에서 0.3초로 감소했고, 물체 배치부터 효과 투사까지 걸리는 시간은 1초 이내로 줄었습니다. RTX 3060 PC 한 대에서 투사 화면 30 FPS와 추론 처리 15 FPS를 유지하며, YOLO 인식률은 96%로 감지 성능 손실이 없었습니다. 현재 가시광 IP 카메라 2대와 디스플레이 2대로 시범 설치 운영 중입니다.

공식 오픈 전 프로젝트이므로 실제 화면과 내부 프로젝트명은 공개하지 않습니다.
