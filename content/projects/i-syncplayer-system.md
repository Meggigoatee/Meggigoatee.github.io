## 프로젝트 핵심 스택

i-syncPlayer System은 여러 Windows 장비에서 이미지와 비디오를 함께 재생하고, 중앙 장비에서 각 플레이어의 상태와 업데이트를 관리하는 전시 운영 시스템입니다. 중앙 통제 앱인 i-playerHub와 현장 재생 앱인 i-syncPlayer를 하나의 사례로 구성했습니다.

- 중앙 운영: 플레이어 등록, 상태 모니터링, 장비별·일괄 명령
- 동기 재생: 각 존의 마스터·클라이언트 사이에서 이루어지는 재생 준비와 시간 보정
- 콘텐츠 운영: 로컬 미디어 카탈로그와 다중 플레이리스트 관리
- 내부망 업데이트: 릴리스 검증, 파일 제공, 장비별 다운로드와 설치 지시

2026년 7월 31일부터 8월 21일까지 개인 프로젝트로 진행했습니다. 기존 i-syncPlayer 소스코드를 인수해 개선하는 동시에, 여러 플레이어를 한곳에서 운영하기 위한 i-playerHub를 직접 제안하고 신규 개발했습니다. 현재 오픈 예정인 전시관에서 여러 존으로 나뉜 플레이어 PC 12대와 허브 PC 1대, 프로젝터 27대 구성으로 시범 운영 중입니다.

## 배경과 해결하려던 문제

여러 화면이 하나의 장면처럼 동작하는 전시에서는 같은 재생 버튼을 누르는 것만으로 충분하지 않습니다. 장비마다 미디어 준비 시간이 다르고, 영상 재생 시간이 조금씩 어긋날 수 있으며, 일부 장비나 네트워크가 응답하지 않더라도 나머지 화면과 운영 도구는 계속 동작해야 합니다.

운영 측면에서는 현장 장비를 한 대씩 확인하거나 새 버전을 직접 설치하는 부담도 있습니다. 이 시스템은 재생 동기화와 중앙 운영을 서로 다른 책임으로 나눕니다. 플레이어는 여러 존으로 구성되며, 각 존에서 하나의 i-syncPlayer가 마스터가 되어 같은 존에 속한 클라이언트들의 재생을 맞춥니다. i-playerHub는 존 구분과 관계없이 각 장비의 상태와 업데이트를 직접 관리합니다. 따라서 특정 존이나 마스터의 상태가 중앙 관리 전체를 막지 않도록 구성되어 있습니다.

## 담당 범위

기존 i-syncPlayer를 여러 장비에서 운영하기 위한 중앙 통제 방식과 i-playerHub 도입을 직접 제안했습니다. UI·그래픽 디자인에는 참여하지 않았으며, 개발 범위는 i-playerHub의 신규 개발과 기존 i-syncPlayer 소스코드의 인수·개선입니다.

두 애플리케이션에서 담당한 구현 범위는 다음과 같습니다.

- Electron 기반 중앙 통제 앱과 현장 재생 앱
- 플레이어 등록, 상태 폴링, 원격 명령과 설정 화면 연결
- TCP 명령 채널과 UDP 시간 채널을 사용한 존별 마스터·클라이언트 재생 동기화
- 미디어 카탈로그, 다중 플레이리스트와 이미지·비디오 재생
- 내부망 업데이트 저장소, 파일 서버와 장비별 설치·이전 버전 적용 흐름
- TypeScript 모듈의 Vitest 단위 테스트와 Windows 설치 패키징

## 시스템 흐름

이 시스템에는 목적이 다른 두 네트워크 흐름이 공존합니다.

1. i-playerHub는 등록된 각 i-syncPlayer의 상태를 직접 조회합니다.
2. 운영자는 중앙 화면에서 선택한 장비 또는 전체 장비에 확인·설치 같은 명령을 보냅니다.
3. 재생 중에는 각 존의 i-syncPlayer 마스터가 같은 존에 속한 클라이언트에 미디어 준비와 재생 명령을 전달합니다.
4. 같은 존의 클라이언트는 준비 완료 여부를 응답하고, 재생 중에는 해당 존의 마스터가 보낸 시간 정보로 로컬 재생 속도를 보정합니다.

상단 시퀀스 다이어그램은 Hub가 여러 존의 장비를 각각 직접 관리하는 흐름과 각 존의 Master·Clients 사이에서 이루어지는 준비·재생·시간 보정을 구분합니다.

## 핵심 구현

### 1. 재생 토폴로지와 분리한 중앙 장비 관리

i-playerHub는 플레이어의 마스터·클라이언트 관계를 경유하지 않고 각 장비의 HTTP 인터페이스를 직접 호출합니다. 전체 상태 조회와 일괄 명령은 장비별 요청을 병렬로 처리하며, 한 장비의 연결 실패를 예외로 전파하지 않고 해당 장비의 상태값으로 보관합니다. 응답이 늦은 요청에는 제한 시간을 적용하고, 이전 폴링이 끝난 뒤 다음 주기를 예약해 조회 작업이 겹쳐 쌓이지 않도록 했습니다.

설치 명령 직후 플레이어가 종료되어 응답이 도착하지 못할 수 있는 경우와, 명령이 장비에 전달되지 않은 연결 실패도 구분합니다. 중앙 화면이 단순한 성공·실패 표시보다 실제 장비 동작의 경계를 반영하도록 설계된 부분입니다.

### 2. 작업 식별자를 기준으로 한 동기 재생

각 존의 i-syncPlayer 마스터는 재생할 항목을 정한 뒤 같은 존에 연결된 클라이언트가 준비됐는지 확인하고 재생을 시작합니다. 재생 명령에는 작업 식별자를 포함하며, 더 새로운 작업이 시작되면 이전 준비 완료, 종료 이벤트와 시간 패킷을 무시합니다. 빠르게 이전·다음 항목을 선택했을 때 늦게 도착한 응답이 현재 재생을 되돌리는 상황을 막기 위한 구조입니다.

명령과 준비 상태는 TCP 채널로 교환하고, 재생 중의 시간 정보는 UDP 채널로 전달합니다. 클라이언트는 같은 존의 마스터 시간과 로컬 영상 시간의 차이를 재생 속도에 반영합니다. 다음 영상은 두 개의 비디오 요소 중 대기 요소에 미리 준비하고, 해당 존의 장비가 준비되면 활성 요소와 교체합니다. 사전 준비 기능을 지원하지 않는 장비나 이미지 항목에는 기존 전환 경로를 유지합니다.

### 3. 내부망을 전제로 한 검증·배포·설치 흐름

i-syncPlayer의 Windows 릴리스는 설치 파일, 업데이트 메타데이터와 차등 다운로드 정보를 하나의 반입 단위로 묶습니다. i-playerHub는 반입된 릴리스의 버전, 필수 파일과 해시를 검사한 후 업데이트 저장소에 게시하고, 내장 HTTP 서버로 각 플레이어에 제공합니다. 설치 파일을 먼저 배치하고 최신 버전을 가리키는 메타데이터를 마지막에 교체해 게시 도중 불완전한 릴리스가 노출되는 상황을 줄였습니다.

각 플레이어는 새 버전을 백그라운드로 내려받지만 임의로 설치하지 않습니다. 업데이트 적용은 운영자가 중앙 앱에서 명시적으로 실행해야 하며, 허브가 장비별 준비 상태를 확인하고 설치 시점을 지시합니다. 보관된 버전의 메타데이터를 이용한 이전 버전 적용도 같은 장비별 흐름으로 처리하며, 최초 설치와 초기 설정은 현장에서 수동으로 수행하는 범위로 남겨 두었습니다.

### 4. 장비별 콘텐츠 관리

재생 순서는 활성 플레이리스트가 소유하고, 각 항목은 활성화 여부와 볼륨을 가집니다. 파일이 사라진 항목은 목록에 남겨 운영자가 누락을 확인할 수 있게 하되 실제 재생 순환에서는 제외합니다. 클라이언트는 마스터가 보낸 플레이리스트 순번으로 자기 장비의 항목을 찾기 때문에, 장비마다 다른 영상 파일을 같은 순서로 맞춰 재생할 수 있습니다.

## 기술 선택과 트레이드오프

- **중앙 관리와 존별 재생 동기화 분리:** 특정 존의 마스터 상태와 무관하게 다른 플레이어를 점검하고 업데이트할 수 있습니다. 대신 중앙 관리용 HTTP 계약과 플레이어 간 동기화 프로토콜을 각각 관리해야 합니다.
- **TCP 명령과 UDP 시간 정보:** 준비·재생 명령은 순서를 보장하고, 반복되는 시간 정보는 가볍게 전달합니다. 네트워크 상태와 장비 성능에 따른 실제 동기 정확도는 현장 검증이 필요합니다.
- **순번 기반 장비별 미디어 매핑:** 화면마다 다른 파일을 같은 장면 순서로 재생할 수 있습니다. 반면 장비별 플레이리스트의 항목 수와 순서를 운영자가 일치시켜야 하며, 현재 구현에는 장비 사이의 파일 체크섬 비교가 없습니다.
- **이중 비디오 사전 준비:** 다음 영상을 대기 요소에 로드해 전환 시점의 준비 지연을 줄입니다. 동시에 두 영상 자원을 유지해야 하고, 기능을 지원하지 않는 클라이언트가 있으면 대체 흐름을 사용합니다.
- **내부 파일 서버 기반 업데이트:** 인터넷 연결이 없는 환경에서도 중앙 장비에서 배포할 수 있습니다. 최초 설치와 릴리스 반입은 수동이며, 다운로드 중에는 중앙 파일 서버가 실행 중이어야 합니다.

## 테스트·배포·운영 안정성

두 애플리케이션 모두 TypeScript와 Vitest 기반 테스트를 갖고 있습니다. i-playerHub 쪽에서는 장비 목록 검증, 병렬 명령, 중복되지 않는 상태 폴링, 응답 형식 검사, 업데이트 릴리스 검증과 파일 서버의 범위 요청을 다룹니다. i-syncPlayer 쪽에서는 동기화 프로토콜, 오래된 작업 무시, 미디어 사전 준비, 플레이리스트 누락 처리, 원격 제어, 효과 출력과 업데이트 상태 전이를 검사합니다. 현재 콘텐츠 작성 과정에서는 전체 테스트 통과 여부를 새로 실행해 확인하지 않았습니다.

두 앱은 Electron Builder의 Windows NSIS 설치 패키지로 구성되어 있습니다. i-syncPlayer는 자동 업데이트를 지원하고, i-playerHub는 중앙 장비의 업데이트 파일 저장소를 운영합니다.

코드에서 확인되는 안정성 장치는 다음과 같습니다.

- 한 장비의 실패가 전체 상태 조회와 명령을 중단하지 않는 요청 구조
- 이전 주기와 겹치지 않는 폴링, 요청 제한 시간과 중복 명령 방지
- 작업 식별자를 이용한 오래된 동기화 응답과 시간 정보 무시
- 미디어 파일 누락 시 해당 장비를 대기 대상에서 제외하고 나머지 재생 진행
- 설정과 플레이리스트를 임시 파일에 쓴 뒤 교체하는 저장 방식
- 업데이트 파일의 필수 구성과 해시 검증, 최신 메타데이터의 마지막 게시

현재 시범 운영 구성은 여러 존으로 나뉜 플레이어 PC 12대, 허브 PC 1대와 프로젝터 27대입니다. 재생 동기화는 각 존의 Master와 같은 존에 속한 Clients 사이에서 이루어지며, 존별 동기화 오차는 0.1초 미만입니다. 업데이트는 운영자의 명시적인 실행을 거쳐 적용합니다. 장기간 운영 결과와 장애 복구 기록은 전시관 정식 운영 이후 확인할 항목입니다.

## 의사결정과 결과

### 문제

단일 영상을 반복 재생할 때 루프 경계에서 약 1초의 지연이 발생했습니다. 이로 인해 약 1초 동안 모든 영상이 멈춘 것처럼 보여 사용자 경험에 크게 악영향을 끼쳤습니다.

### 대안 소개

- 하나의 `video` 요소에 기본 루프를 적용해 같은 파일을 반복 재생하는 방식
- 두 개의 `video` 요소를 활성·대기 상태로 운용하고, 다음 영상이나 반복할 같은 영상을 미리 준비한 뒤 교체하는 방식

### 결정 이유

두 개의 `video` 요소를 사용하는 이중 버퍼 방식을 선택했습니다. 현재 영상이 재생되는 동안 대기 요소에 다음 영상이나 반복할 같은 영상을 미리 로드하고, 재생 경계에서 활성 요소와 교체하도록 구성했습니다. 이를 통해 파일을 다시 준비하는 시간이 화면 공백으로 이어지는 것을 줄였습니다. 또한 단일 영상 반복과 여러 영상 전환을 별도 모드로 나누지 않고 기존의 준비·교체 로직을 함께 재사용해 상태 전이와 동기화 코드를 단순화하고 유지보수성을 높였습니다.

### 결과

단일 영상의 루프 재생 지연을 0.05초 미만으로 줄였습니다. 현재 여러 존으로 나뉜 플레이어 PC 12대를 시범 운영하고 있으며, 각 존의 Master와 Clients 사이에서 동기화 오차를 0.1초 미만으로 유지하고 있습니다.
