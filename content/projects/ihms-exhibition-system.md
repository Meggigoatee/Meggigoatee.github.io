## 프로젝트 핵심 스택

전시장 한 곳을 하나의 시스템으로 운영하기 위한 Windows 데스크탑 애플리케이션 세 개로 구성됩니다. 통제 PC에서 동작하는 중앙 콘솔 i-hms, 각 전시 PC의 트레이에 상주하는 에이전트, 그리고 여러 화면의 이미지·비디오 재생을 맞추는 i-syncPlayer입니다. 세 프로그램 모두 Electron 기반이며 Windows 설치 패키지로 배포합니다.

- 중앙 통제: 전원 시퀀스, 장비 사양 조회, 원격 명령과 로그를 한 화면에서 처리
- 콘텐츠 운영: 재생할 영상과 효과를 중앙에서 각 전시 PC의 재생 폴더까지 반입
- 동기 재생: 각 존의 마스터·클라이언트 사이에서 이루어지는 재생 준비와 시간 보정
- 폐쇄망 업데이트: 릴리스 검증, 내부망 파일 제공, 장비별 순차 설치와 이전 버전 적용

2026년 7월부터 개인 작업으로 진행하고 있습니다. 기존 i-syncPlayer 소스코드를 인수해 개선하고, 이미 전시장에서 운영되던 i-hms에 사양·영상관리·플레이어 화면을 새로 만들어 장비와 콘텐츠, 업데이트를 한 콘솔에서 통제하도록 정리했습니다. 현재 오픈 예정인 전시관에서 여러 존으로 나뉜 플레이어 PC 12대, 통제 PC 1대와 프로젝터 27대 구성으로 시범 운영 중입니다.

## 배경과 해결하려던 문제

여러 화면이 하나의 장면처럼 동작하는 전시에서는 같은 재생 버튼을 누르는 것만으로 충분하지 않습니다. 장비마다 미디어 준비 시간이 다르고, 영상 재생 시간이 조금씩 어긋날 수 있으며, 일부 장비나 네트워크가 응답하지 않더라도 나머지 화면과 운영 도구는 계속 동작해야 합니다.

운영 측면의 부담은 더 컸습니다. 전시장에는 이미 전원과 프로젝터, 조명을 다루는 i-hms 콘솔이 있었지만, 재생할 영상을 바꾸거나 플레이어 새 버전을 설치하는 일은 조작자가 PC를 한 대씩 돌며 처리해야 했습니다. 인터넷이 없는 폐쇄망이라 일반적인 배포 경로도 쓸 수 없습니다.

그래서 시스템을 세 가지 책임으로 나눴습니다. 재생 동기화는 플레이어끼리만 처리하고, 각 PC에서 실제 작업을 실행하는 일은 에이전트가 맡고, 사람이 보는 화면과 모든 지시의 발신은 i-hms 한 곳으로 모읍니다. 조작자는 장비 종류나 작업 종류와 관계없이 같은 콘솔을 사용하고, 특정 존이나 마스터의 상태가 중앙 운영 전체를 막지 않습니다.

## 담당 범위

UI·그래픽 디자인에는 참여하지 않았습니다. 개발 범위는 기존 i-hms의 기능 확장과 기존 i-syncPlayer 소스코드의 인수·개선이며, 각 전시 PC의 에이전트에 대해서는 i-hms가 보내는 명령 규격을 정의하고 연동하는 부분을 담당했습니다.

- i-hms 사양 화면: 각 PC의 CPU·RAM·디스크·GPU·OS와 프로젝터 모델·램프 시간 조회, 결과 캐시와 CSV 내보내기
- i-hms 영상관리 화면: 전시 PC별 재생 목록과 효과 폴더 편집, 반입·삭제·순서 재배치 오케스트레이션
- i-hms 플레이어 화면: 릴리스 반입·검증·게시, 내부망 업데이트 파일 서버, 장비 상태 조회와 순차 설치·이전 버전 적용
- i-hms 설치 구성: 게시 폴더를 설치 폴더 밖으로 분리하고 필요한 방화벽 규칙을 설치 시 등록하도록 NSIS 스크립트 수정
- i-syncPlayer: 존별 마스터·클라이언트 동기 재생, 파일명 번호 기반 재생 순서와 순서 편집, 이미지 시퀀스 효과, HTTP 제어 API, 내부망 자동 업데이트
- 에이전트 연동: 전원·사양·영상·효과·자체 업데이트 명령의 규격 정의와 i-hms 쪽 구현

## 시스템 흐름

이 시스템에는 목적이 다른 세 가지 경로가 공존합니다.

1. 각 PC의 에이전트는 부팅 직후 같은 대역에서 i-hms를 찾아 전원이 켜졌다고 알립니다. 콘솔은 이 알림으로 화면 상태를 즉시 바꾸기 때문에 전원 상태를 주기적으로 조회하지 않습니다.
2. 조작자가 콘솔에서 내리는 전원, 사양 조회, 영상·효과 반입, 에이전트 자체 업데이트 지시는 각 PC의 에이전트를 거쳐 로컬에서 실행됩니다.
3. 플레이어 업데이트만 에이전트를 거치지 않고 콘솔이 각 플레이어의 HTTP 인터페이스를 직접 호출합니다.
4. 재생 중에는 각 존의 마스터가 같은 존의 클라이언트에 준비와 재생 명령을 보내고, 클라이언트는 준비 결과를 응답한 뒤 마스터가 보낸 시간 정보로 로컬 재생 속도를 보정합니다.

위의 배치도는 세 프로그램이 어느 장비에 설치되고 무엇으로 연결되는지를 보여주고, 시퀀스 다이어그램은 같은 관계를 실제 메시지 순서로 보여줍니다. 두 그림 모두 콘솔이 에이전트와 플레이어를 서로 다른 경로로 지시하는 흐름과, 존 안에서만 이루어지는 준비·재생·시간 보정을 구분합니다.

## 핵심 구현

### 1. 하나의 콘솔, 두 갈래 지시 경로

영상 반입은 파일을 재생 폴더에 넣고 플레이어를 껐다 켜는 작업이라 그 PC에서 실행할 주체가 필요합니다. 그래서 콘솔은 각 PC의 에이전트에 줄 단위 명령을 보내고, 에이전트가 프로세스 종료, 파일 배치, 재시작을 순서대로 수행합니다. 한 PC의 반입 순서는 플레이어 정지, 빼는 파일 삭제, 남는 파일의 번호 재배치, 임시 파일 서버 기동과 신규 파일 전송, 플레이어 재시작입니다.

반면 플레이어 업데이트는 플레이어 자신이 이미 확인·다운로드·설치 인터페이스를 갖고 있어 에이전트를 거칠 이유가 없습니다. 콘솔은 각 장비에 업데이트 서버 주소만 주입하고 이후에는 상태 조회와 확인·설치 지시를 직접 보냅니다. 두 경로를 분리한 덕분에 한쪽이 동작하지 않을 때 원인을 같은 곳에서 찾지 않게 되었고, 에이전트를 교체하는 작업과 플레이어를 교체하는 작업이 서로를 기다리지 않습니다.

콘솔은 플레이어의 마스터·클라이언트 관계를 알지 않습니다. 재생 동기화는 플레이어 전용 채널이므로 콘솔은 장비 목록 순서로 한 대씩 처리하고, 어느 장비를 먼저 갱신할지는 조작자가 정합니다. 반대로 플레이어가 콘솔에 대해 아는 것은 업데이트 서버 주소 문자열 하나뿐이어서, 콘솔이 없는 현장에도 같은 플레이어를 설치할 수 있습니다.

### 2. 슬롯 키를 기준으로 한 동기 재생

각 존의 마스터는 재생할 항목을 정한 뒤 같은 존에 연결된 클라이언트가 준비됐는지 확인하고 재생을 시작합니다. 재생 명령에는 작업 식별자를 포함하며, 더 새로운 작업이 시작되면 이전 준비 완료, 종료 이벤트와 시간 패킷을 무시합니다. 빠르게 이전·다음 항목을 선택했을 때 늦게 도착한 응답이 현재 재생을 되돌리는 상황을 막기 위한 구조입니다.

동기화의 기준은 목록 안의 순번이 아니라 파일명 앞 번호를 정규화한 슬롯 키입니다. 자릿수와 선행 0을 무시하므로 같은 장면을 뜻하는 파일이 장비마다 다른 이름을 갖고 있어도 같은 키로 만납니다. 마스터가 보낸 키에 해당하는 파일이 없는 장비는 준비 대상에서 빠지고, 나머지 장비는 그대로 재생을 이어갑니다.

명령과 준비 상태는 TCP 채널로 교환하고, 재생 중의 시간 정보는 UDP 채널로 전달합니다. 클라이언트는 같은 존의 마스터 시간과 로컬 영상 시간의 차이를 재생 속도에 반영합니다. 다음 영상은 두 개의 비디오 요소 중 대기 요소에 미리 준비하고, 해당 존의 장비가 준비되면 활성 요소와 교체합니다. 사전 준비 기능을 지원하지 않는 장비나 이미지 항목에는 기존 전환 경로를 유지합니다.

### 3. 폐쇄망을 전제로 한 검증·배포·설치 흐름

i-syncPlayer의 Windows 릴리스는 설치 파일, 업데이트 메타데이터와 차등 다운로드 정보를 하나의 반입 단위로 묶습니다. 콘솔은 반입된 릴리스의 버전, 필수 파일과 해시를 검사한 후 게시 저장소에 올리고, 읽기 전용 HTTP 서버로 각 플레이어에 제공합니다. 설치 파일을 먼저 배치하고 최신 버전을 가리키는 메타데이터를 마지막에 교체해 게시 도중 불완전한 릴리스가 노출되는 상황을 줄였습니다.

차등 다운로드는 실패해도 오류를 내지 않고 조용히 전체 다운로드로 넘어갑니다. 100MB가 매번 오가고 있어도 화면은 정상으로 보이기 때문에, 게시 직후 업데이터가 실제로 요청하는 경로들을 직접 확인하는 자체 점검을 붙였습니다. 이전 버전의 차등 정보 파일이 업데이터가 만들어내는 경로에 존재하는지까지 검사합니다.

각 플레이어는 새 버전을 백그라운드로 내려받지만 임의로 설치하지 않습니다. 설치는 조작자가 콘솔에서 명시적으로 실행하며, 콘솔이 장비별 준비 상태를 확인하고 한 대씩 순차로 지시합니다. 한 대가 실패해도 다음 장비로 넘어가고, 실패 사유는 미지원, 무응답, 다운로드 시간 초과, 버전 불일치로 나눠 목록에 남깁니다. 보관된 버전으로 되돌리는 경우에는 대조할 버전을 게시된 최신본이 아니라 그 장비가 받아 둔 버전으로 계산합니다. 최초 설치와 초기 설정은 현장에서 수동으로 수행하는 범위로 남겨 두었습니다.

### 4. 폴더가 소유하는 재생 순서와 순서 편집

재생 순서는 애플리케이션 안의 목록이 아니라 재생 폴더에 있는 파일명의 번호가 소유합니다. 콘솔에서 영상을 반입할 때도 목록 순서대로 앞 두 자리를 다시 매겨 폴더에 남기고, 플레이어는 시작할 때 폴더를 한 번 읽어 목록을 만듭니다. 조작자가 기존에 사용하던 영상 반입 방식과 같은 규칙이라 운영 절차를 바꾸지 않아도 됩니다.

플레이어에서 순서를 바꾸는 것도 결국 파일 이름을 바꾸는 일입니다. 그래서 순서 편집은 먼저 전체 이름 변경 계획을 세우고, 목록 밖의 파일을 덮어쓰거나 번호를 뗄 수 없는 이름이 섞여 있으면 파일을 하나도 옮기지 않고 거절합니다. 실제로 옮길 때는 재생을 멈추고 미디어 요소의 소스를 비워 파일 잠금을 풀며, 잠금 오류가 남아 있으면 간격을 늘려 여섯 번까지 다시 시도한 뒤 실패 시 전부 되돌립니다. 자리를 맞바꾸는 경우에는 임시 이름을 거쳐 두 단계로 옮기고, 임시 이름은 번호로 시작하지 않게 만들어 중간에 중단되더라도 재생 목록에 끼어들지 않습니다. 영상별 효과도 같은 번호를 따르므로 효과 폴더의 번호를 함께 재배치합니다.

## 기술 선택과 트레이드오프

- **중앙 통제와 존별 재생 동기화 분리:** 특정 존의 마스터 상태와 무관하게 다른 장비를 점검하고 갱신할 수 있습니다. 대신 콘솔이 갱신 순서를 자동으로 정하지 못해 조작자가 목록 순서로 선택합니다.
- **에이전트 경유와 직통 경로의 공존:** 파일 배치처럼 로컬 실행이 필요한 작업과 플레이어가 이미 제공하는 기능을 각각 적합한 경로로 처리합니다. 대신 두 경로의 계약을 따로 관리해야 하고, 조작자에게도 둘이 다른 경로임을 알려야 합니다.
- **TCP 명령과 UDP 시간 정보:** 준비·재생 명령은 순서를 보장하고, 반복되는 시간 정보는 가볍게 전달합니다. 네트워크 상태와 장비 성능에 따른 실제 동기 정확도는 현장 검증이 필요합니다.
- **파일명 번호가 소유하는 재생 순서:** 기존 운영 방식과 호환되고 장비마다 다른 파일을 같은 장면 순서로 재생할 수 있습니다. 반면 콘솔의 번호 재배치와 플레이어의 순서 편집이 같은 번호 공간을 쓰기 때문에, 나중에 반입하는 쪽이 앞의 순서를 덮어씁니다. 코드로 막을 수 없어 운영 규칙으로 다룹니다.
- **이중 비디오 사전 준비:** 다음 영상을 대기 요소에 로드해 전환 시점의 준비 지연을 줄입니다. 동시에 두 영상 자원을 유지해야 하고, 기능을 지원하지 않는 클라이언트가 있으면 대체 흐름을 사용합니다.
- **폐쇄망 전제와 평문 명령 채널:** 인터넷 없이도 중앙에서 배포할 수 있고 인증 절차가 운영을 방해하지 않습니다. 대신 에이전트 명령 채널에 인증이 없어 내부망 격리에 의존합니다. 외부망과 연결되는 구성으로 확장할 때 가장 먼저 손봐야 할 부분으로 남겨 두었습니다.

## 테스트·배포·운영 안정성

i-syncPlayer는 TypeScript와 Vitest 기반 단위 테스트를 갖고 있습니다. 동기화 프로토콜, 오래된 작업 무시, 미디어 사전 준비, 슬롯 키 정규화와 순서 편집 계획, 파일 누락 처리, 원격 제어, 효과 출력과 업데이트 상태 전이를 검사합니다.

i-hms는 테스트 프레임워크 없이 기능별 하네스로 검증했습니다. Electron 스텁 위에서 메인 프로세스를 그대로 구동해 릴리스 반입, 파일 서버, 게시 자체 점검과 장비 캐시를 확인하고, 실제 업데이터를 이 서버에 물려 차등 다운로드를 재현했습니다. 약 101MB 설치 파일을 약 2.1MB만 받아 재구성하고 해시가 게시본과 일치하는 것을 확인했습니다. 순차 설치는 가짜 플레이어 여러 대로 실패 사유 분기까지 검증하고, 화면은 jsdom으로 렌더링해 버튼 활성화 규칙과 다국어 키 누락을 확인했습니다. 실제 장비를 대상으로 한 지시·재기동 검증은 아직 진행하지 않았습니다.

세 앱 모두 Windows NSIS 설치 패키지로 배포합니다. i-hms와 i-syncPlayer에는 기기 종속 라이센스 검증과 바이트코드·번들 암호화 기반의 코드 보호가 적용되어 있고, 에이전트는 보호 없이 배포합니다. 업그레이드 시 설치 폴더가 통째로 삭제되는 설치 관리자 동작 때문에, 반입한 릴리스를 보관하는 게시 폴더는 설치 폴더 밖으로 분리하고 필요한 방화벽 규칙은 설치 시점에 등록하도록 했습니다.

코드에서 확인되는 안정성 장치는 다음과 같습니다.

- 한 장비의 실패가 전체 조회와 순차 작업을 중단하지 않는 요청 구조
- 요청 제한 시간, 중복 명령 방지와 응답 형식 검증
- 작업 식별자를 이용한 오래된 동기화 응답과 시간 정보 무시
- 미디어 파일 누락 시 해당 장비를 대기 대상에서 제외하고 나머지 재생 진행
- 순서 편집의 사전 계획 검사, 두 단계 이름 변경과 실패 시 되돌리기
- 설정과 상태를 임시 파일에 쓴 뒤 교체하는 저장 방식
- 업데이트 파일의 필수 구성과 해시 검증, 최신 메타데이터의 마지막 게시

현재 시범 운영 구성은 여러 존으로 나뉜 플레이어 PC 12대, 통제 PC 1대와 프로젝터 27대입니다. 존별 동기화 오차는 0.1초 미만이며, 업데이트는 조작자의 명시적인 실행을 거쳐 적용합니다. 장기간 운영 결과와 장애 복구 기록은 전시관 정식 운영 이후 확인할 항목입니다.

## 의사결정과 결과

### 문제

단일 영상을 반복 재생할 때 루프 경계에서 약 1초의 지연이 발생했습니다. 이로 인해 약 1초 동안 모든 영상이 멈춘 것처럼 보여 사용자 경험에 크게 악영향을 끼쳤습니다.

### 대안 소개

- 하나의 `video` 요소에 기본 루프를 적용해 같은 파일을 반복 재생하는 방식
- 두 개의 `video` 요소를 활성·대기 상태로 운용하고, 다음 영상이나 반복할 같은 영상을 미리 준비한 뒤 교체하는 방식

### 결정 이유

두 개의 `video` 요소를 사용하는 이중 버퍼 방식을 선택했습니다. 현재 영상이 재생되는 동안 대기 요소에 다음 영상이나 반복할 같은 영상을 미리 로드하고, 재생 경계에서 활성 요소와 교체하도록 구성했습니다. 이를 통해 파일을 다시 준비하는 시간이 화면 공백으로 이어지는 것을 줄였습니다. 또한 단일 영상 반복과 여러 영상 전환을 별도 모드로 나누지 않고 기존의 준비·교체 로직을 함께 재사용해 상태 전이와 동기화 코드를 단순화하고 유지보수성을 높였습니다.

### 결과

단일 영상의 루프 재생 지연을 0.05초 미만으로 줄였습니다. 현재 여러 존으로 나뉜 플레이어 PC 12대를 시범 운영하고 있으며, 각 존의 Master와 Clients 사이에서 동기화 오차를 0.1초 미만으로 유지하고 있습니다.

## 구조 의사결정과 결과

### 문제

여러 플레이어의 상태를 확인하고 새 버전을 설치하려면 중앙 화면이 필요했습니다. 처음에는 플레이어 전용 중앙 앱을 별도로 제안해 신규 개발했지만, 전시장에는 이미 전원과 장비를 다루는 i-hms 콘솔이 조작자의 기본 화면으로 자리 잡고 있었습니다.

### 대안 소개

- 플레이어 전용 중앙 앱을 유지하고 통제 PC에서 콘솔 두 개를 함께 운영하는 방식
- i-hms에 플레이어 화면을 신설해 통제 콘솔을 하나로 유지하는 방식

### 결정 이유

i-hms로 통합하는 방식을 선택했습니다. 조작자가 작업 종류에 따라 화면을 바꿔 쓰지 않아도 되고, 영상 반입에 필요한 에이전트 명령과 장비 목록, 로그 화면을 이미 i-hms가 갖고 있어 같은 자산을 재사용할 수 있습니다. 통제 PC에서 실행되는 애플리케이션이 하나로 유지되면 라이센스와 설치·코드 보호 구성도 한 벌만 관리합니다. 대신 플레이어 전용 앱에서 만든 구조를 그대로 옮기지 못하고, 게시 저장소와 업데이트 파일 서버를 i-hms의 설정·설치 구성에 맞춰 다시 구현해야 했습니다.

### 결과

플레이어 상태 조회, 릴리스 게시, 순차 설치와 이전 버전 적용을 i-hms 안에서 처리하고 별도 중앙 앱은 사용하지 않습니다. 통합 과정에서 업데이트 파일 서버가 영상 배포용 임시 파일 서버와 포트가 겹쳐 실행이 실패하는 문제를 확인해 두 서버의 포트를 분리했고, 기존 설치본이 갖고 있던 포트 설정은 실행 시 새 값으로 옮기도록 했습니다.

대표 이미지와 실제 실행 화면은 공개 자료가 준비되면 추가할 예정입니다.
