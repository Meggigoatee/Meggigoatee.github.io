# i-hms 전시 통합 운영 시스템 조사 메모

2026-09-22 재조사. 이전 문서(`i-syncplayer-system.md`)는 중앙 통제 앱을 `i-playerHub`로 기록했으나, 사용자 확인 결과 해당 앱은 사용하지 않는다. 중앙 통제는 기존 전시장 콘솔인 `i-hms`가 맡고, 각 전시 PC에는 플레이어와 별개로 실행되는 에이전트 프로그램이 상주한다.

## 사용자 확인 정보

- 프로젝트 형태: 개인 프로젝트
- 담당 범위: 기존 i-hms 기능 확장 개발, 기존 i-syncPlayer 소스코드 인수 후 개선, 에이전트 명령 규격 정의와 연동
- 에이전트(localcontrol) 앱 자체의 개발은 담당 범위로 적지 않는다
- UI·그래픽 디자인 참여: 없음
- 운영 상태: 오픈 예정 전시관에서 시범 운영 중
- 운영 구성: 플레이어 PC 12대, 통제 PC 1대, 프로젝터 27대
- 동기화 오차: 0.1초 미만
- 업데이트 정책: 조작자의 명시적 실행을 통해 적용
- 에이전트 소스: 저장소의 사본은 구 버전이며, 전체 기능을 설명하는 근거로만 사용한다
- 대표 의사결정: 단일 영상 반복 시 약 1초의 지연 문제에 대해 이중 `video` 버퍼를 선택해 0.05초 미만으로 감소

## 조사 대상

읽기 전용으로 조사했으며 원본 저장소를 수정하지 않았다.

- 중앙 콘솔: `D:\workspace\RnD\i-hms`
- 각 PC 에이전트: `D:\workspace\RnD\i-hms_agent`
- 현장 재생 앱: `D:\workspace\RnD\i-syncPlayer`

기준 문서는 `i-hms/.references/system-overview.md`(세 저장소가 맞물리는 방식), `i-hms/.references/player-update.md`(플레이어 원격 업데이트 계약과 실측), `i-hms/AI_WORKLOG.md`(변경 이력), `i-syncPlayer/.references/architecture.md`이다.

## 확인한 근거

### i-hms (통제 PC 1대)

- `package.json`: 이름 `i-hms`, 설명 "통합 전원 제어 시스템", Electron 27, NSIS perMachine 패키징. 의존성은 `serialport`, `ping`, `node-arp`, `wol`, `bytenode`. 테스트 프레임워크는 없다
- 화면은 메인·설정·사양·영상관리·업데이트·플레이어·로그 탭으로 구성된다(`src/index.html`)
- `AI_WORKLOG.md` 기준 이번 작업의 추가분: 사양 탭(2026-07-17), 사양 CSV 내보내기와 결과 캐시, 캐시 경쟁 상태 수정(2026-07-18), 영상관리 탭과 이펙트 하위 탭(2026-07-20), 업데이트 탭의 버전 자동 갱신, 플레이어 탭과 원격 업데이트 일체(2026-09-11), 설치 경로·게시 폴더 분리와 방화벽 규칙 등록(2026-09-11)
- 전원 시퀀스는 프로젝터·AC ON → PC WOL → relay ON → 확인 순서이며 OFF는 역순이다. PC를 켜는 것은 WOL, 끄는 것은 에이전트 명령이다
- 프로젝터는 PJLink와 AT 명령으로 모델·램프 시간을 조회하고, 조명·스크린은 시리얼 포트를 사용한다
- 영상 배포 오케스트레이션: 플레이어 정지 → 삭제 → 번호 재배치 → 임시 파일 서버 기동과 전송 → 플레이어 재시작. 최종 파일명은 목록 순서대로 앞 두 자리를 `00`부터 다시 매긴다
- 플레이어 업데이트는 에이전트를 거치지 않고 각 플레이어의 HTTP API를 직접 호출한다. 게시 저장소는 설치 폴더 밖에 두고, 업데이트 파일 서버는 상시 기동한다
- 검증 방식은 `node --check`, Electron 스텁 하네스, 실제 `electron-updater` 연동, 가짜 플레이어 다중 롤아웃, jsdom 패널 렌더 테스트다

### 에이전트 (각 전시 PC)

- `i-hms_agent/package.json`: 이름 `localcontrol`, Electron 27, NSIS perMachine. 코드 보호 구성은 없다
- `index.js`: 트레이 상주 앱이며 TCP 서버를 고정 포트로 연다. 명령은 줄 단위 평문이고 인증이 없다
- 저장소 사본에서 확인되는 명령은 `turnoff`, `restart`, `wolstatus`(WOL 설정과 화면 수·해상도), `version`, `update:<ip>:<port>:<exe|zip>`이다
- 부팅 직후 저장된 서버 IP를 확인하고 실패하면 같은 `/24` 대역을 스캔해 콘솔을 찾은 뒤 `poweron`을 보낸다. 콘솔은 이 알림으로 전원 상태를 갱신하므로 폴링이 없다
- 자체 업데이트는 설치 파일을 받아 `.cmd` 헬퍼를 띄우고 자신을 종료한 뒤 무인 설치하고 재실행한다
- `system-overview.md`는 현장 버전에 `specs`, `iplayerinfo`, `iplayerstop/start`, `movie*`, `effect*` 명령이 있다고 기록한다. 저장소 사본은 구 버전이라 이 명령들이 없다. 공개 콘텐츠에서는 명령 목록을 나열하지 않고 "전원·사양·영상·효과·자체 업데이트 명령"으로만 서술했다

### i-syncPlayer (각 전시 PC)

- `package.json`: 이름 `i-syncplay` 1.9.1, Electron·TypeScript·Vitest·esbuild·jsdom 구성, 의존성은 `bytenode`, `electron-updater`, `ws`
- 테스트 파일 25개가 있다
- 재생 순서는 재생 폴더 파일명의 번호가 소유하며, 동기화 참조는 순번이 아니라 번호를 정규화한 슬롯 키다
- 마스터는 TCP로 `set`/`prepare`/`play`를 보내고 UDP로 재생 시간을 전파한다. 명령과 시간 패킷에 작업 식별자가 포함되어 오래된 응답을 무시한다
- 순서 편집은 실제 파일 이름 변경이다. 사전 계획 검사, 재생 정지와 소스 비우기, 잠금 오류 재시도, 두 단계 이름 변경과 되돌리기를 구현한다
- 효과는 `effects/<번호>/<시퀀스>` 폴더의 이미지 시퀀스이며 좌표를 UDP로 받아 Canvas에 그린다
- 자동 업데이트는 백그라운드 다운로드까지만 자동이고 설치는 외부 지시 시점에 수행한다. 플레이어가 아는 것은 업데이트 서버 주소 문자열 하나뿐이다
- 선택적으로 Spout 공유 텍스처를 내보내 Unity 수신기에서 표시한다

## 사실과 표현 판단

### 공개 초안에 사용한 사실

- Electron 기반 Windows 앱 세 개(중앙 콘솔·에이전트·플레이어)로 구성됨
- 콘솔이 유일한 발신자이고, 에이전트 경유 경로와 플레이어 직통 경로가 나뉨
- 부팅 알림으로 전원 상태를 반영해 폴링을 쓰지 않음
- 슬롯 키 기반 존별 동기 재생과 작업 식별자
- 폴더가 소유하는 재생 순서와 이름 변경 기반 순서 편집
- 폐쇄망 릴리스 검증·게시·순차 설치와 실패 사유 분류
- 차등 다운로드 실측(약 101MB 설치 파일 중 약 2.1MB 수신, 해시 일치)
- NSIS 패키징, 기기 종속 라이센스와 코드 보호, 에이전트는 보호 없음

### 사용하지 않거나 보정한 표현

- 실제 포트 번호, 내부 IP, 설치 경로, 전시장명, 클라이언트명은 공개 콘텐츠에 넣지 않았다
- 이전 초안의 "플레이리스트 순번으로 항목을 찾는다"는 서술은 사실과 달라 "슬롯 키"로 정정했다
- 이전 초안의 "두 앱 모두 Vitest 테스트를 갖고 있다"는 서술은 i-hms에 해당하지 않아 하네스 기반 검증으로 정정했다
- i-playerHub 관련 서술은 모두 제거하고, 통합 결정을 의사결정 항목으로 옮겨 적었다
- "실시간 완전 동기화", "무중단 업데이트", "현장 안정성 검증 완료" 같은 표현은 근거가 없어 사용하지 않았다
- 에이전트 명령 채널에 인증이 없다는 사실은 위험 요소로만 서술하고 구체적인 공격 경로는 적지 않았다

## 다이어그램 데이터

시퀀스 다이어그램의 참여 요소는 i-hms 콘솔, PC 에이전트, 플레이어-Master, 플레이어-Client 네 개다. 콘솔에서 에이전트로 가는 지시, 콘솔에서 플레이어로 직접 가는 지시, 존 안의 준비·재생·시간 보정을 구분해 배치했다. 에이전트가 먼저 말을 거는 경우는 부팅 알림뿐이므로 첫 메시지로 두었다.

## 실행하지 않은 검증

- 세 저장소의 테스트, 타입 검사, Windows 빌드를 이 작업 중에 새로 실행하지 않았다
- 실제 장비와 내부망에서의 동작은 확인하지 않았다
- 운영 구성 수치(PC 12대, 프로젝터 27대)와 동기화 오차는 사용자 확인 정보를 그대로 사용했다

## 추가 확인이 필요한 정보

- 실제 실행 화면과 대표 이미지의 공개 가능 범위
- 시범 운영 구성 수치가 i-hms 통합 이후에도 동일한지
- 정식 운영 이후의 장기 운영 기간과 장애 복구 기록
