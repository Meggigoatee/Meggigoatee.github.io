# 프로젝트 콘텐츠 QA

## 검토 기준과 상태

- 기준 문서: `docs/portfolio-content-plan.md`
- 근거 문서: `docs/research/*.md`
- 공개 초안: `content/projects/*.md`
- 검토 범위: frontmatter 스키마와 순서, 메인·서브 섹션, 미확인 역할·기간·성과, 민감정보, 문체·맞춤법, 다이어그램 접근성과 중복
- 현재 상태: 최종 검토 — 7개 모두 확인
- 확인한 초안: i-syncPlayer System, 미디어테이블, 황금마패의 길, Tobomi, 완도 AI 아바타 생성 프로그램, B the B LIVE WALL, 정읍 방문자센터 마을 만들기
- 종합 판정: 콘텐츠 초안 7개 모두 계획서의 필수 구조와 사실·보안 원칙을 충족한다. 사용자 확인이 필요한 역할·기간·팀·운영 성과는 별도 질문으로 보완해야 한다.

## 전체 공통 점검

### Frontmatter 스키마와 순서

- 7개 문서는 `content.config.ts`의 필수 필드를 모두 가진다. 계획서 공통 필드에는 없지만 실제 스키마가 요구하는 `order`도 모두 존재한다.
- 메인 4개는 `featured: true`, 서브 3개는 `featured: false`로 분류가 맞다.
- `order`는 1~7로 중복 없이 이어진다.
- 문경 문서만 필드 순서가 `slug → category → status → featured → order`이고 나머지는 `slug → order → category → status → featured`다. 파싱에는 영향이 없지만 작성 규칙의 일관성을 위해 최종 정리 시 통일할 수 있다.
- `role: 확인 필요`, `team: 확인 필요`, `status: 확인 필요`는 사용자 확인 전 초안 값으로 유지한다. 메인 에이전트가 UI에서 값이 `확인 필요`일 때 숨기도록 처리하기로 했으므로, 이 정책이 적용되면 미확인 정보가 사실란에 노출되는 문제는 없다.
- 다이어그램 제공 방식은 두 가지다. i-syncPlayer와 문경은 구조화된 `diagram` frontmatter를 사용하고, Icecream Table과 Tobomi는 본문에 제목·텍스트 대체 설명·구조화된 표를 제공한다. 후자의 표는 단계/계층, 처리 책임과 연결 관계를 헤더가 있는 DOM 텍스트로 완전히 전달하므로 접근 가능한 구조화 다이어그램으로 인정한다.

### 섹션 충족

- 메인 4개는 모두 한눈에 보기, 배경/문제, 담당 범위, 흐름, 핵심 구현 4개, 기술 선택/트레이드오프, 테스트/배포/안정성, 의사결정/결과를 포함한다.
- 서브 3개는 모두 목적, 담당 범위, 기술 스택, 핵심 구현 4개, 핵심 판단/결과를 포함한다. 대표 이미지 데이터는 `cover: null`로 준비되어 있으며 개발 환경에서만 빈 슬롯을 보이는 현재 상세 페이지 정책과 맞는다.
- 메인 문서의 제목은 대체로 통일되어 있으나 Tobomi만 `테스트·배포·안정성`, 나머지는 `테스트·배포·현장 안정성`이다. 개인 앱의 성격상 의미는 자연스럽지만 탐색 구조를 엄격히 통일하려면 제목을 맞출 수 있다.
- Icecream Table과 Tobomi에는 별도 `추가 확인이 필요한 정보` 섹션이 없다. 필수 본문 구조는 충족하며 확인 사항이 결과 문단에 들어 있으므로 누락은 아니지만, 사용자 확인 질문을 프로젝트별로 수집하려면 별도 섹션을 두는 편이 취합에 유리하다.

### 확인되지 않은 역할·기간·성과

- 7개 모두 `period: null`이며, 확인되지 않은 기간을 단정하지 않는다.
- Tobomi의 `team: 개인 프로젝트`는 계획서에 명시된 사실과 일치한다. 나머지 팀 구성과 개인 역할은 모두 `확인 필요`로 구분했다.
- 구현 범위를 개인 기여로 오인하지 않도록 “저장소에서 확인되는 구현 범위”와 “개인 기여 범위와 동일하다고 단정하지 않음”을 명시한 점이 적절하다.
- 납품·출시·운영 성과, 사용자 반응, 성능 향상, 비용 절감 등의 미확인 성과를 사실처럼 쓴 문장은 발견하지 못했다.
- “기술적 결과”와 “코드에서 확인되는 결과”는 구현 상태를 요약하는 문맥으로 사용되어 정량 성과 주장과 구분된다.

### 민감정보

- 공개 초안에서 내부 IP, 포트 번호, API 키, 인증 헤더, 서버 주소, 로컬 절대 경로, 프린터명, 클라이언트 식별 정보는 발견하지 못했다.
- 완도 문서는 로컬 공유 서버와 임시 터널, 만료 시간 등 구조를 공개하지만 주소·포트·인증정보는 제외했다. 현재 수준은 기술 설명으로 볼 수 있으나, 외부 서비스/보안 구조 공개 범위를 클라이언트와 별도로 확인하는 것이 안전하다.
- 문경 문서는 QR 허용 호스트 검증을 설명하면서 실제 호스트명을 노출하지 않아 적절하다.
- Tobomi 문서는 시스템 활동 감지 범위를 설명하지만 입력 내용·키 종류·창 제목·화면을 수집하지 않는다는 제한을 함께 밝혀 개인정보 관련 오해를 줄인다.
- B the B 문서는 실제 API 주소·인증값·해시태그·계정명·게시물 ID·캡션·이미지 URL을 노출하지 않는다. 다만 소셜 게시물의 공개·삭제·필터링 정책은 기술 구현과 별개이므로 사용자 확인 항목으로 유지해야 한다.
- 정읍 문서는 내부 카메라 접속 정보, IP·포트, 모델 파일과 운영 임계값을 노출하지 않는다.

### 문체와 맞춤법

- 전반적으로 존댓말 서술형, 기술명 원문 표기, 사실/확인 필요 구분이 일관적이다.
- 현재 검토에서 명백한 맞춤법 오류는 발견하지 못했다.
- “개인의 정확한 담당 범위”, “본인의 정확한 담당 범위”, “정확한 개인 담당 역할”이 혼용된다. 최종 교정에서 “본인의 정확한 담당 범위”처럼 한 표현으로 통일할 수 있다.
- 영문 기술 표기에서 `portable`만 일반 영문 소문자로 쓰인다. 공식 빌드 명칭을 유지하려는 의도라면 문제없지만, 한국어 문장에서는 “포터블 패키지”로 통일하는 선택지도 있다.
- 본문에 확인 필요 문장이 반복되어 초안의 신뢰성은 높지만, 최종 공개본에서는 사용자 답변 반영 후 반복을 줄여 읽는 흐름을 다듬어야 한다.

### 다이어그램 접근성과 중복

- i-syncPlayer와 문경의 `diagram`에는 제목, 설명, `ariaLabel`, 각 노드/단계의 텍스트가 있어 계획서의 접근성 요구를 충족한다.
- Icecream Table과 Tobomi의 본문 표에는 단계/계층, 책임과 연결 관계가 텍스트로 제공되어 비시각 사용자도 내용을 이해할 수 있다.
- 구조화된 다이어그램이 렌더링되는 문서에서 본문 흐름 설명과 다이어그램 설명이 일부 반복되지만, 현재 수준은 시각 자료의 텍스트 대체와 본문 맥락 제공이라는 서로 다른 목적이 있어 과도한 중복은 아니다.
- i-syncPlayer의 단일 `Spout · Unity Receiver` 노드에 Master와 Clients가 모두 연결되어 실제로 하나의 수신기를 공유하는 것처럼 읽힐 수 있다. `ariaLabel`에는 각 플레이어의 선택적 출력이라고 설명하므로, 시각 컴포넌트에서도 “장비별 선택적 출력”이 드러나는지 확인해야 한다.
- Icecream Table과 Tobomi의 표는 시각 장식보다 정보 구조와 접근성을 우선한 다이어그램이다. 별도 `ProjectDiagram`을 중복 추가할 필요는 없으며, 향후 그래픽 컴포넌트로 바꾸는 경우에만 동일한 표를 함께 노출해 중복시키지 않도록 한다.

## 프로젝트별 판정

### i-syncPlayer System

- 판정: 통과, 다이어그램 표현 1건 확인 필요
- 계획서의 WebSocket 설명과 달리 공개 초안은 실제 조사 근거에 따라 TCP/UDP와 HTTP로 정정되어 있다. 잔존 의존성만으로 WebSocket을 기술 스택에 넣지 않은 판단이 적절하다.
- 중앙 관리와 재생 동기화를 분리해 설명하며, 역할·운영 상태·장비 수·동기 정확도를 단정하지 않는다.
- 다이어그램의 Receiver 노드가 장비별 선택 경로임을 시각적으로도 명확히 해야 한다.

### Icecream Table

- 판정: 통과
- 메인 프로젝트 필수 8개 영역과 핵심 구현 4개를 충족한다.
- 테스트 존재와 테스트 통과를 구분하고, 실제 배포·인식 성능·운영 성과를 확인 필요로 남겼다.
- 본문의 제목, 텍스트 대체 설명과 3열 구조화 표가 Camera Input부터 Display Output까지의 단계와 전달 값을 완전히 표현하므로 접근 가능한 다이어그램 기준을 충족한다.

### 황금마패의 길

- 판정: 통과, frontmatter 순서만 경미한 불일치
- 기술 구조보다 관람객 여정을 우선한 계획서 방향을 정확히 따른다.
- QR 진입 여부와 스탬프 획득 조건, 기기 내 사진 저장 등 핵심 구현의 근거가 조사 노트와 일치한다.
- 실제 배포·지원 기기·운영 결과를 단정하지 않으며 실제 허용 호스트도 노출하지 않는다.

### Tobomi

- 판정: 통과
- `status: 개발 중`, `team: 개인 프로젝트`가 계획서와 일치하고 출시·다운로드를 완료 상태로 표현하지 않는다.
- 구현된 메모·타이머·집중 기능과 미구현 리마인더·캘린더를 명확히 구분한다.
- 본문의 제목, 텍스트 대체 설명과 3열 구조화 표가 Vue UI/Pinia부터 Rust Services와 네이티브 분기까지의 계층·책임·연결을 완전히 표현하므로 접근 가능한 다이어그램 기준을 충족한다.

### 완도 AI 아바타 생성 프로그램

- 판정: 통과, 공개 범위 확인 1건 권고
- MediaPipe의 실제 사용 범위를 얼굴 검출로 제한하고, 배경 제거·68점 얼굴 좌표는 별도 서비스 응답으로 구분해 과장하지 않았다.
- 테스트 자동화가 확인되지 않았음을 명시했고 납품·생성 성공률·처리 시간을 단정하지 않는다.
- 임시 터널을 포함한 결과 공유 구조는 기술적으로 구체적이므로 클라이언트 공개 허용 범위와 얼굴 사진/결과물의 실제 보관·삭제 정책을 사용자에게 확인해야 한다.

### B the B LIVE WALL

- 판정: 통과, 게시물 공개 정책 확인 권고
- 서브 프로젝트 필수 구조와 핵심 구현 4개를 충족한다. 해시태그별 수집 실패 분리, ID 중복 제거, 고정 슬롯 순환과 현장 레이아웃 보정이 조사 근거와 일치한다.
- 외부 API와 게시물의 실제 식별 정보를 공개하지 않았고, 테스트 파일의 존재와 실행 통과 여부를 구분했다.
- 외부 서비스 이용 정책과 게시물 노출 동의·필터링·삭제 요청 처리 방식은 소스만으로 확인할 수 없으므로 공개 전 사용자 확인이 필요하다.

### 정읍 방문자센터 마을 만들기

- 판정: 통과
- 서브 프로젝트 필수 구조와 핵심 구현 4개를 충족하며, 감지 안정화·MST 연결·PixiJS 레이어·교차/충돌 배치의 근거가 조사 노트와 일치한다.
- 베지어 모듈이 저장소에는 있지만 현재 PixiWorld에서 호출되지 않는 사실을 명시해 “베지어 이동 적용 완료”로 과장하지 않았다.
- 내부 카메라·모델·네트워크 설정을 공개하지 않았고, 납품·성능·장기간 운영 결과를 확인 필요로 남겼다.

## 최종화 전 체크리스트

- 모든 frontmatter 필드 순서를 선택적으로 통일한다. 현재 순서 차이는 파싱과 렌더링에는 영향을 주지 않는다.
- UI에서 `확인 필요` 상태·역할·팀 값이 숨겨지는지 확인한다.
- 7개 문서의 사용자 확인 질문을 중복 제거해 한 번에 요청할 목록으로 취합한다.
- 공개 전 클라이언트명과 화면, 네트워크/외부 서비스 구조, 생체 이미지 처리, 소셜 게시물 노출 정책의 공개 가능 범위를 확인한다.
- 사용자 답변을 반영한 뒤 반복되는 “확인 필요” 문장을 줄이고 최종 맞춤법 교정을 진행한다.
